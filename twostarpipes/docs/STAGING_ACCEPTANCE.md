# Staging acceptance: execute only after the relevant approvals

No live result is recorded here. Use a dedicated staging project and synthetic fixtures. Before starting, review `security/STAGING_PLAN.md`, complete preflight, obtain each migration approval, configure services and separately approve a staging deployment. Never run this checklist against production by default.

Record project reference, deployed application revision, SQL revision, tester, date and pass/fail evidence without credentials or customer contact records. Use an owner-controlled `example.com` fixture mailbox only if actual delivery to it is intended; otherwise use an approved test inbox. Do not send to fabricated/unapproved recipients.

For each failed step, stop the affected rollout. Keep public INSERT denied, RLS enabled and existing rows intact. Pause notifications when delivery is uncertain; preserve queue/audit evidence. Do not delete live/customer records as cleanup. Any synthetic-fixture removal also requires explicit approval.

For local visual artifacts, set `$env:QA_SCREENSHOTS='1'` before `npm.cmd run test:e2e`, then `Remove-Item Env:QA_SCREENSHOTS`. Use only synthetic data and adequate free disk space. This changes screenshot capture only; test assertions are always enabled.

Do not approve production SQL, merge/push, domain changes or deployment based only on local tests. Review live evidence and approve each operation separately.
